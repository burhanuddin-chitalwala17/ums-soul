# ADR-04: ADRs as one-file-per-decision; specs in `docs/specs/`

- **Date:** 2026-07-07
- **Status:** Accepted — **spec-layout portion superseded by [ADR-05](0005-spec-convention.md)** (2026-07-12): specs moved from numbered flat files to feature folders with a spec/TRD split. The *ADR-folder* decision below still stands.
- **Origin:** New cross-service decision. Applies to every repo in the workspace (soul + each service). **Amended same day (2026-07-07):** specs centralized in `soul/docs/specs/` rather than per-service — reflected in the Decision and the new alternative below. (Amended in place rather than superseded: same session, nothing had been built on the earlier wording yet.)
- **Context:** ADRs were accumulating in a single `ADR.md` per repo. As Phase 2 begins to spawn multiple specs (SPEC-02, SPEC-03, SPEC-04) and more decisions land, a single growing file has two problems: (1) it becomes a long scroll that's awkward to diff, link to, and supersede within; (2) there was no concrete home for per-spec detail — `docs/specs/` was referenced across the docs but never created, so phase/spec detail had nowhere to go and risked being crammed into `BACKLOG.md`. The question raised: split the backlog by phase, split ADRs into a folder, or both?
- **Decision:** 
  - **ADRs → one file per decision** in an `adr/` folder in each repo, named `NNNN-<kebab-title>.md` (zero-padded to the ADR number), with an `adr/README.md` index (number · title · status · date) that also carries the format spec and the "how to add" rules. Each repo keeps its own ADR sequence starting at ADR-01, unchanged by this migration. This matches how ADRs behave — append-only, individually superseded, frequently cross-referenced.
  - **Specs → `soul/docs/specs/`** (project-wide, **one global SPEC sequence** across all services), one file per SPEC (`SPEC-NN-<slug>-trd.md`), with a `docs/specs/README.md` index. Specs are forward-looking planning artifacts that pair with `BACKLOG.md` and may span services (the Phase 3 WebSocket/REST contract, the Phase 5 feedback loop), so they do not belong inside any single service repo. *Which* service implements a spec is a field in the TRD, not the file's location. This establishes the model: **soul = planning + cross-service context (backlog, specs, cross-service ADRs); services = implementation (code, tests, service-internal ADRs, service CHANGELOG).**
  - **`BACKLOG.md` stays a single file** — it is the one-screen, cross-phase status *map*; splitting it by phase would destroy its at-a-glance value and duplicate status tracking. Per-phase detail belongs in specs, not in a split backlog.
- **Alternatives considered:**
  - *Split `BACKLOG.md` into a per-phase folder* — rejected. The backlog's entire purpose is the single top-down view; a folder would force opening N files to answer "where are we" and create two places where status drifts. The detail the split was meant to capture belongs in `docs/specs/`, which already existed in the design.
  - *Keep ADRs in a single `ADR.md`* — fine at 3–4 records, but the file-per-decision convention (Nygard / MADR / `adr-tools`) scales better and fits the append-only/supersede model; migrating now while the count is small is cheap.
  - *Do nothing until it hurts (YAGNI)* — the specs folder was already needed for SPEC-02 (imminent), so this is need-driven, not speculative.
  - *Specs in each service's `docs/specs/` (route by scope, like ADRs/CHANGELOGs)* — considered and rejected. It optimizes for the rare single-service spec at the cost of the cross-service ones (Phase 3 contract, Phase 5 feedback loop) that would otherwise have to relocate mid-life, and it fragments the "all planned work in one place" view that pairing specs with `BACKLOG.md` gives. Accepted the resulting asymmetry (specs + backlog centralize in soul; ADRs + CHANGELOGs still federate by scope) as deliberate: a spec is product-grade planned work, whereas a service-internal ADR is local implementation detail.
- **Consequences:**
  - ✅ Each ADR is an individually linkable, stable, diff-friendly artifact; the index gives the at-a-glance list the single file used to provide.
  - ✅ `soul/docs/specs/` gives phase/spec detail a real home, keeping `BACKLOG.md` thin, and never needs to relocate when a spec turns out to span services.
  - ✅ Clean separation: `BACKLOG.md` = status map, `soul/docs/specs/` = detail, `adr/` = decisions. One global SPEC sequence, no per-service numbering collisions.
  - ⚠️ Deliberate asymmetry: specs + backlog centralize in soul while ADRs + CHANGELOGs federate by scope. Justified (product-planning vs implementation-detail) but worth remembering so it doesn't read as drift.
  - ⚠️ Adding an ADR is now "create a file + add an index row" instead of "append to one file" — the `/ums-sdlc adr-new` flow and the skill docs are updated to match.
  - ⚠️ Historical references to `ADR.md` in append-only CHANGELOGs and ADR "Origin" notes are left intact (they describe past state); only live/structural references were repointed to `adr/`.
